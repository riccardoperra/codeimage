# Local AI

A request in plain words, such as "add a tab test.tsx with this code …, use Dracula, padding 32, export PNG 2x", becomes editor changes. Chrome's on-device model (Prompt API, Gemini Nano) calls the editor's agent tools natively, and the page runs each call through the same registry that browser agents use. Nothing leaves the browser and there is no cloud fallback.

## Sub-features

The experiment switch, the on-device model row under it, the Ask AI button in each desktop layout's action bar, the command, and the inline bar that takes the action bar's place: a request field (Enter sends, Shift+Enter breaks the line, Esc closes and gives the focus back to Ask AI), Send and Close. The bar opens over the action bar, which stays in the layout hidden under it, so the canvas never moves; the bar and its list draw above the canvas. Above the bar, a list shows the request, Thinking… while the model works, a first read-only row for the editor state the model received (`get_editor_state`, summed up as `1 tab · index.tsx · Dracula`), the model's own words before a call, each call as running then done or failed with its localized title, the raw tool name, an argument summary and the tool's error, then the model's answer as plain text, clamped to 3 lines with Show all. A run stops after 6 turns of calls and says so. A new request clears the list. The floating agent activity card does not repeat these calls. No Ask AI on a phone (768 px and narrower): no button, no command, no bar.

`model.ts` is the model-agnostic API (`ModelProvider.availability(tools)`, `ModelProvider.open({system, tools, history, signal})`, `ModelSession.stream(input)` yielding `text-delta`, `tool-call` and `done` events). `agent.ts` holds the loop as a reducer over a `Run` (phase, entries, text): at send time it reads a short brief of the editor (tabs, theme, each setting by flat name with its value, theme names; `createEditorBrief` in `tools.ts`) and passes it as the answer to a `get_editor_state` call, opens a session with the 11 tools, runs each call, sends the results back and continues until the model stops or 6 turns pass. Rows are keyed by a run-unique id, because Gemma reuses `call_0` every turn or sends an empty callId; the model's own callId goes back unchanged. The loop refuses `export_image` with `The request did not ask for an export.` unless the request names an export (`asksForExport`). `chrome-provider.ts` is the only code that knows the Prompt API: `availability()` asks with the same tools and expected types that `create()` gets, one base session per system prompt and tools, cloned for each request, the state appended as an assistant tool call and its `LanguageModelToolSuccess`, `promptStreaming()` for every turn (text chunks taken as deltas or as the text so far), `LanguageModelToolSuccess`/`LanguageModelToolError` for results, and `[local-ai]` console logs of each step, with every call the model makes logged as JSON (`model called {"callId","name","arguments"}`) and every result sent back as JSON (`tool results sent back [{callId, name, ok, output}]`). A rejected `create()` reads as `Chrome could not start the on-device model. Check free disk space and chrome://on-device-internals.` (InvalidStateError) or `Chrome's on-device model can't run tools in this browser.` (anything else), with the raw error in the console.

## How to get to it (user POV)

Only in a browser that exposes `LanguageModel`; without it the Local AI group is hidden. Settings → Experiments → Local AI → Use local AI. The On-device model row under the switch says where the model stands: ready, needs a download (Download model), downloading with a progress bar (indeterminate with `Downloading… Chrome doesn't report progress yet.` and a copy chip for chrome://on-device-internals, which shows the live download status, until Chrome reports progress above 0, then the bar and a percentage), cannot run here (`Chrome says it cannot run on this device.`) with Check again, or failed with the error and Retry. A download Chrome reports without progress, and that this page did not start, offers Restart download, which calls `create()` again from the click. While the model is unavailable, downloadable or failed, the row lists Chrome's requirements (Chrome 148+ on desktop; Windows 10/11, macOS 13+, Linux or ChromeOS on a Chromebook Plus; more than 4 GB of VRAM or 16 GB of RAM; 4+ cores; about 20 GB free; On-device AI on), each marked met, not met or check yourself from what the page can read (`userAgentData` high-entropy hints, `hardwareConcurrency`, `deviceMemory`, which Chrome caps at 8 and which never decides memory alone, since a GPU with more than 4 GB of VRAM also qualifies; disk space, VRAM and the Chrome setting are never readable), and two copy chips for chrome://settings/ai and chrome://on-device-internals, since a page cannot open chrome:// addresses. `local-ai/requirements.ts` holds the rules, with unit tests. The switch stays off and disabled until the model is available. The page asks `availability()` on load and on each visit to Experiments, polls it every 5 s while a download runs, and never calls `create()` when it answers `unavailable`. Only the Download model click, or a request when the model is already `available`, calls `create()`. Ask AI and the command menu's Ask local AI… show only once the model is available and the experiment is on, on an editable snippet, on a computer. The bar never downloads: if the model is not available it says so and links to Experiments.

## Driving it with Playwright

`VERIFY_AUDIT=1 VERIFY_CASES=local-ai node .agents/skills/verify-codeimage/scripts/verify.mjs`

Every context installs a fake `LanguageModel` with `clone()`, `append()` and `promptStreaming()`, plus fake `LanguageModelToolCall`, `LanguageModelToolSuccess` and `LanguageModelToolError` classes, by init script. It streams scripted chunks per request: text (the second chunk repeats the first, as cumulative text would), then `tool-call` parts, and records the base sessions, clones, appended history and every prompt.

The first Inspector context downloads the model from Experiments (progress 0, then 0.5, then ready, with the requirement list and chips as before), turns the switch on, opens the bar from Ask AI and checks focus, Shift+Enter and that the field keeps its keys. The canned request reuses callId `call_0` across two turns and sends empty callIds. It must show thinking, the read-only `get_editor_state` row first, each of `add_tab`, `apply_theme`, `set_controls` and `export_image` running then done with its summary, a failing `read_tab` with its own error (a reused callId must not overwrite another row), the model's note once, and the answer; CodeMirror shows the code in a new `test.tsx` tab, the theme is Dracula, the padding changed and the downloaded PNG is the frame at 2x. The fake must have one base session with the 11 tools, no editor state in its system prompt, no worked examples (a small model copied them literally), `availability()` asked with the options `create()` got, a history append whose `get_editor_state` call and success share a callId and carry the brief with dot-free setting names and the theme names, and tool responses carrying `call_0`, `''` and `call_1` as sent. The brief must be under a third of `get_editor_state`'s size; the case returns both sizes. A second request applies the theme Nope: its row fails, the `LanguageModelToolError` sent back carries `bad-1` and the error, the answer shows, and the base session was created once and cloned twice. A third request calls a tool every turn and must stop at 7 rows (the state, then 6 turns) with `Stopped after 6 turns`. Esc closes and focuses Ask AI; the command reopens an empty bar with the field focused.

The second context loads while Chrome downloads and becomes available by polling. Its fake then rejects `create()` with InvalidStateError: the bar must show the disk-space message. Then it answers `downloadable`: the bar must say the model is not ready and Open experiments must land on Download model. The third context covers the failed download and the unavailable requirements as before.

Three more contexts open the bar in Inspector, Dock and Studio at 1440 px: the frame must not move, the bar must stay on screen with no horizontal scroll, and the list must sit above the bar. The z-order over the frame, the answer clamp and the Format button are checked by hand. Three phone contexts at 390 px assert that neither Ask AI nor the command exists. Evidence: `local-ai-{inspector,dock,studio}-{idle,thinking,running,done}.png`, `local-ai-answered.png`, `local-ai-failed.png`, `local-ai-turn-limit.png`, `local-ai-2x.png`, the `local-ai-row-*.png` files and the traces.

Source: `pages/UnifiedEditor/local-ai/` (`model.ts`, `agent.ts`, `chrome-provider.ts` and `language-model.ts` with unit tests; `LocalAi.tsx` the button, the bar and the list), `agent-tools/ToolActivity.tsx` for the shared `ToolRow`, `controls/CanvasToolbar.tsx` where the bar replaces the action bar, `shell/sections.tsx` for the Experiments rows and `agent-tools/tools.ts` for the tools.

## Gotchas

The system prompt carries one-line recipes that map common requests to single tool calls (duplicate_tab {} for a copy, set_animate_mode for record or animate), and a unit test keeps every tool name it mentions in the registry. Each tool description ends with an `Also for:` line of synonyms.

The fake model proves the wiring, the Prompt API message shapes and the effects, not Gemini Nano's choices. The explainer does not say whether `promptStreaming()` yields tool-call parts or whether text chunks are deltas; the `[local-ai]` console lines show the real chunks. A fresh Playwright profile reports the model as `downloadable`, so a real run needs the maintainer's Chrome. The full `get_editor_state` measures about 7,200 characters for the default editor; the brief the bar seeds is a fraction of that, which matters for a small context. Setting option values are the store's keys, so `window_shadow` takes raw CSS strings; its labels are accepted too. The What's new Nudge can announce in the moment between closing Settings and opening the bar; the audit dismisses it.
